# Prototype Real Modules Plan

**Audience:** Thomas, who decides how the Prototype runs a module, where its sample data comes from and what replaces the copies; experience-design, which builds the Prototype's side (the page, the sample host, the Planner section); server-development, which builds the read-only route for a module's parts, the shared sample data and the check; content-manager, which updates the design system pages' README and the Prototype section of plan-design-system once each step lands.

**Status:** Draft, 2026-10-30. This plan proposes; Thomas decides. Thomas decided the goal on 2026-10-30: the Design System Prototype (`public/design-system/prototype.*`) shows the real module code running against sample data, instead of a copy of the module's markup. His reason: the Prototype's Planner section holds copied templates and copied stylesheets, drifts and breaks on its own, and he had to find Prototype bugs by eye. Everything else below, including the approach, is a proposal until he answers the questions at the end.

## What it is today

- **The page.** `public/design-system/prototype.html` and `prototype.js` draw module frames with the real `createModuleFrame` (`public/module-frame.js`): four sample states, a tabs sample, the title bar actions, then the Planner section. A theme, Light or Dark, a width (390, 500, 700, 1280) and the "Light: current / proposed" switch are chosen at the top and kept in the address (`?theme=&mode=&w=&look=`). The page is served without sign-in, on a single-environment install and on the product host (`PRODUCT_DOMAIN`; `server/index.js`, the `DESIGN_SYSTEM_FILES` allow-list and the `/design-system/` and `/sdk/` rules).
- **The Planner section is a copy.** `public/design-system/prototype-planner.js` (611 lines) holds 29 templates copied character for character from `modules/travel/src/travel.html`, and re-implements what `travel.js` does with them (`buildDay`, `buildCard`, `buildPhaseMarker`, `phaseJoints`, `renderStrip`, the date strip's arrows, the `.narrow` and `.tiny` width rule). Its sample (a week in Lisbon, `SAMPLE`, `BANDS`, `MARKERS`, `DECISIONS`, `BOOKINGS`) is its own, not the screenshot seed. Its stylesheets come from `window.DS_SOURCES` in `public/design-system/sources.js`, a file written by `node tools/design-system-snapshot.mjs --sources`. Its icons come from `DS_SOURCES.svgs`. The toolbar's views, the status line and the "Hide empty days" icon are written again in `prototype.js` (`PLANNER_VIEWS`, `PLANNER_TITLE`, `plannerStatus`, `planBar`).
- **The parity check.** `tools/check-prototype-parity.mjs` (25 to 46 seconds) boots the screenshot seed (`bootSeeded('travel', ...)` from `tools/shots.mjs`), adds a few objects the seed lacks, opens the real Planner (`/modules/travel?space=`) and the Prototype's, and measures: (1) the same parts have the same edges and heights in both, (2) columns line up, (3) the joint's + is centred, (4) phone taps are 44 pixels, (5) the Prototype answers its container width, not the window, (6) the copied templates equal `travel.html` and `sources.js` equals what the stylesheets produce. Parts (1) and (6) exist only because the Planner section is a copy. It catches geometry and copy drift, not drift in what the copy does (a new slot, a changed hide rule, a new class set by `travel.js`).
- **How the real Planner runs.** A bundled module runs in the page, not in a frame (`server/modules.js`, `runModeOf`). `public/module-host.js` `mountModule` fetches its parts from `/m/<id>/<version>/<entry>?part=css|body|js` (the server splits the installed module's built page; `server/index.js`, `app.get('/m/:id/:version/*path')`), puts the styles and markup in a shadow root (`startInPage`), builds the module's SDK with `window.createHost({ call, root, rootElement, ... })` from `public/sdk/host.js`, and starts the script with `script.host` set. Every SDK call goes through `call(method, params)` to the `handlers` object in `mountModule` (about 90 names: `hello`, `storage.*`, `objects.*`, `toolbar.set`, `header.set`, `status.set` ...), which makes the real requests. `createFrameBands` (exported) draws the module's "+", title bar icons, toolbar and status into its `createModuleFrame`.
- **The seam already exists.** `createHost` takes any `call`. `hostCurrency.select` in `public/sdk/host.js` already builds a host with a small `call` of its own for a page that has no module. The Planner (`modules/travel/src/travel.js`, `travel-lib*.js`) makes no request of its own: no `fetch`, no `EventSource`; everything goes through `host.*`. On its first draw it uses about 30 calls: `hello`, `storage.list`, `storage.get`, `objects.resolve`, `objects.links`, `objects.search`, `people`, `settings.get`, `lookup.available`, `budget.elsewhere`, `actions.list`, `events.*`, `phases.cover`, `facts.set`, `icons.svg`, and the frame's `toolbar.set`, `header.set`, `add.set`, `status.set`, `setTitle`, `resize` (read as code only; step 4 records the real list).
- **The built page.** `server/module-build.js` `buildModule` joins `src/<id>.html` with the lib's and the page's stylesheets and scripts (`/*__CSS__*/`, `/*__JS__*/`, `/*__LIB__*/`, `LIB_<NAME>` data). The server installs a bundled module from that. Nothing serves a module's parts without an installed, enabled module, and `/m/` is not let through on the product host.
- **The seed.** `tools/shots-seed.mjs` `seedServer(call)` writes the travel seed through the API: the template, three members, the phases on fixed days (computed from the template's phase list), and objects for Planner, Places, To-do, Polls, Calendar, Budget and Research, each with a fixed key (`plan:a1`). The chat is written into `DATA_DIR` afterwards. The fixed day is 2026-10-15 (`TODAY`), the server's clock (`shots-clock.cjs`) and the page's are frozen on it. The values live inline in the script, not in a data file.
- **`sources.js` has a second reader.** The Design System page (`index.html`, `ds.js`) reads `DS_SOURCES` too: the module stylesheets for its usage lists, the icon list and their SVGs. `tools/check-design-system.mjs` warns when it is older than the stylesheets.
- **The Artifact build.** `tools/prototype-artifact.mjs` builds the Prototype as a static folder. It follows only absolute imports (`'/x.js'`) and copies `style.css` and `system.css`; it does not copy `prototype-planner.js` (a relative import), `sources.js` or `host.css`, so the Planner section probably does not draw in the Artifact today. Read as code only, not opened.

## Decisions

1. **The Prototype shows the real module.** Its module sections run the module's own code (its script, markup and stylesheets from `modules/<id>/src`, unchanged) against sample data, instead of a copy of its markup (Thomas, 2026-10-30).
2. **The copies go.** `prototype-planner.js` and the Planner's copied pieces in `prototype.js` are removed, not kept beside the new section; the parity check's copy assertions go with them (Thomas, 2026-10-30, with the no-compatibility rule in `CLAUDE.md`).
3. **No regeneration step.** Nothing in the Prototype's module sections is written by a script and committed; a change to the module shows on the next reload (Thomas, 2026-10-30).

## The approach: three options

What "run the real module" can mean. Each runs the module's own `travel.js`, `travel.html` and stylesheets; they differ in what answers the module's calls.

**(a) An in-page sample host.** The Prototype builds the module's SDK with `window.createHost`, as `module-host.js` does, with a `call` of its own that answers every SDK call from sample data held in the tab. The module's parts come from a read-only route that builds them from `modules/<id>/src` with the server's own builder. The module's bands are drawn by the real `createFrameBands` into the Prototype's real `createModuleFrame`.
- Fidelity: the module's code, the SDK, the frame and the shadow root setup are the product's. What is not the product's: the answers to the calls (the shapes `module-host.js` and the server give), and the summaries the server makes of other modules' objects (`objects.resolve`, `objects.links`). A check compares the result with the real Planner (below), so a wrong answer shows as a difference.
- Cost: moderate. One sample host (about 30 calls for the Planner, more per module later), one route, the seed's values moved to a data file, the check rewritten.
- Offline: works with no data directory, no sign-in, no LiveKit, and as a static Artifact (the parts and the sample data become files at build time).
- Product host: let through the new parts route, `/phases.js` (the SDK loads it for `host.util.phaseTimeline`) and a path for icon SVGs (`/api/icons` needs a signed-in person).
- Rules out: showing what the server computes live (a new summary rule shows only once the sample data or the check is updated).

**(b) A sample API on the server.** The Prototype runs the real `mountModule` unchanged; the server answers `/api/modules/<id>/context`, `/data`, `/api/objects/resolve`, the stream and the rest from sample data, for `/design-system/` only.
- Fidelity: higher on the page side (the real `handlers` run). The server side is a second implementation of the API's answers, larger than (a)'s, and it is still not the real server.
- Cost: high. Every route the module touches, the event stream, the module's identity (the module mounts as if installed), a way to tell a sample request from a real one.
- Offline: needs the server; no static Artifact.
- Risk: an unauthenticated, API-shaped surface in the production server, beside the real one, on the product host too. A mistake in telling the two apart reads or writes real data. The no-compatibility rule's spirit (one path) is strained by a parallel API.

**(c) A throwaway seeded space.** The Prototype opens the real Planner in a space seeded as the checks do (`bootSeeded`).
- Fidelity: complete; it is the product.
- Cost: low to build, high to run: a server with its own `DATA_DIR`, a sign-in, 20 seconds or more to seed, LiveKit settings. Thomas would sign in to a sample environment to look.
- Offline: no. Not on the product host, not in the Artifact, not without a server. The theme and width switches would drive another page.
- Rules out: the Prototype as a page anyone can open.

**Suggestion: (a).** It keeps the Prototype a page that opens anywhere without sign-in and without data, runs the module's own code unchanged, adds no API, and its one remaining second source (the answers) is held by a check against (c)'s real Planner, which the parity check already boots. (b) costs more and carries the most risk; (c) is what the check does, and should stay there. This is question 1.

## The contract

Written for option (a). Where a question below would change a part, it says so.

### The module's parts (server-development)

- **One builder.** `server/module-build.js` gains the page builder `buildModule` already holds inside (`build(name)`), exported, so the install and the Prototype build a page the same way. The split of a built page into `css`, `body` and `js` in the `/m/` route moves into one function in `server/module-build.js`, used by `/m/` and by the new route. Replace, do not copy: `/m/` calls the function, its answers do not change.
- **Route.** `GET /design-system/modules/:id/:entry?part=css|body|js`. `:id` must be a bundled module (a folder under `modules/` that `bundledModules` lists) whose manifest runs in the page; `:entry` must be one of its manifest's surface entries (`page.html`, `canvas.html`). It builds from `modules/<id>/src` at request time and answers the part with `Cache-Control: no-cache` and `X-Content-Type-Options: nosniff`. Anything else is `404` with a plain `not found`. It reads no `DATA_DIR`, needs no sign-in, does not care whether the module is installed or enabled in any environment, and has no write method.
- **Also served for the Prototype:** the module's manifest as `GET /design-system/modules/:id/module.json` (the sample host reads the name, icon, permissions and setting defaults from it rather than from a copy), and the template's public parts as `GET /design-system/templates/:id.json` (its phases and words; question 4).
- **Product host.** The new routes, `/phases.js` and the icon path (question 9) are let through on the product host, beside today's `/design-system/` and `/sdk/` rules. A single-environment install (no `BASE_DOMAIN`) serves them as it serves `/design-system/` today.
- **Status codes.** `200` with the part; `404` for an unknown module, an uploaded module, an unknown entry or an unknown part; `405` is not needed (only `GET` is routed).

### The sample data (server-development)

- **One source.** The travel seed's values move from `tools/shots-seed.mjs` into a data file under `public/design-system/fixtures/` (question 3), so the browser can load it and Node can read it: the template id, the people (logins and names, no passwords), the space (name, description), the phase days by phase id, and the stored objects by module and key (`travel` `plan:a1` ...). Ids the server makes are written as placeholders (`{space:trip}`, `{person:mia}`) that the seed resolves against the server's answers and the sample host resolves against fixed ids. Dates are written as days.
- **The seed reads it.** `seedServer` writes the same objects through the API, as now; only where the values come from changes. The passwords, the AI key placeholder and the chat stay in `tools/shots-seed.mjs` (the chat goes straight into `DATA_DIR`, which the Prototype never has). The games seed is not touched by this plan.
- **What the server derives.** Answers the server computes from stored objects (the summaries of linked objects, the links of a plan entry, the module's setting values) are written in the same file under `derived`, keyed by the call. The check compares them with the real server's answers for the same seed and names the one that differs.
- **The extras.** The objects the parity check adds today (a buffer, a travel day, a free day, rows from Calendar, an undated object per phase) live in the same file, as a layer the Prototype and the check both apply (question 3).
- **Nothing real.** Invented names only (the seed's own: Mia Alvarez, Sam Okafor, Lee Chen, Lisbon). No password, key, token, email address or address of a real person. The new check (part 5) fails on a value in the file that looks like a key, a token or an email address.

### The sample host (experience-design)

A new file, `public/design-system/sample-host.js`, imported by `prototype.js`. It exports `mountSample({ module, entry, frame, container, fixture })`.

- **Start.** It uses the same in-page start the product uses: `startInPage` is lifted out of `mountModule` in `public/module-host.js` as an exported function taking `{ container, parts, call, liftUp }`, and `mountModule` calls it. Replace, not alongside: there is one in-page start. The parts' addresses are the only difference (`/m/...` for the product, `/design-system/modules/...` for the Prototype).
- **Bands.** The module's "+", title bar icons, toolbar and status are drawn by the real `createFrameBands` into the Prototype's `createModuleFrame`, so the Planner's own view switch, title and "Hide empty days" show, not the Prototype's.
- **The answers.** Every call the module makes is one of four kinds:
  - **Read from the sample:** `hello` (the person, the permissions from the manifest's defaults for the role, the module, the space and its phases, the template's phase list, the locale with the template's words, the theme from `readTheme`), `storage.get`, `storage.list`, `objects.resolve`, `objects.links`, `objects.search`, `objects.kinds`, `people`, `spaces`, `settings.get`, `actions.list`, `events.since`, `budget.elsewhere`, `presence.get`, `icons.svg`.
  - **Written in the tab only** (question 5): `storage.set` and `storage.delete` change the sample in memory and send the module the `change` event the stream would; `objects.setLinks`, `facts.set`, `facts.clear`, `attention.set`, `attention.clear` and `lookup.remember` answer as the product does and keep nothing. A reload starts again from the file.
  - **Drawn by the page:** `toolbar.set`, `header.set`, `add.set`, `status.set`, `standard.set`, `setTitle`, `resize`, `ui.toast` (the page's note), `ui.confirm` (the real `confirm.js` dialog), `share.show` and `print.run` (the real `module-actions.js`, as the title bar section already uses).
  - **Not in the Prototype:** `lookup.available` answers `false`; `lookup.flight`, `lookup.airport`, `ai.*`, `chat.ask`, `uploads.*`, `geocode.*`, `preview.*`, `media.watch`, `actions.request`, `objects.open`, `page.open` reject with "Not in the Prototype." and the page's last-action line says which call it was.
  - A call the sample host does not know rejects with "Not in the Prototype: <call>", is shown on the page, and fails the check.
- **No request leaves the tab.** The sample host never calls `api()`, `fetch` on `/api/`, or `EventSource`. Its only requests are `GET`s of the parts, the manifest, the template's public parts, the sample data file, `/phases.js` and icon SVGs. The check fails on any other request from the Prototype.
- **The clock** (question 6): the module reads `Date` as the product does; the Prototype pins it to the sample's day before the module starts, so "today" is the same every time and matches the screenshots.
- **Themes, modes and widths.** The theme file and `data-theme-mode` are set on the page's `html`, as today; the tokens reach the shadow root by inheriting, as in the product. On a switch the page fires `app:theme`, which `module-host.js` already turns into the SDK's `theme` event. The width switch sets the frame's width; the module answers its container itself (its own `.narrow` and `.tiny`), as in the product. Nothing in the module's code or styles knows it is in the Prototype.
- **The Prototype's own looks.** The "Light: proposed" sets and any look being tried stay in `prototype.css`. Tokens on `html` reach the module by inheriting. Rules that must reach inside the module's shadow root are appended by the page, after the module's own styles, as one `<style>` holding `prototype.css`; the product's code gets no hook for it.
- **The jump list** (question 8): the Prototype keeps its "Jump to" buttons, each naming a selector in the real module's markup and the view it is in. Changing the view goes through the module's own toolbar event (`bands.event`), not a Prototype function. The check fails when a target is not found.

### The check (server-development)

`tools/check-prototype-parity.mjs` keeps its name and its place in `npm run check`; its contents change.

1. **Same input, same markup.** It boots the seed (as now), opens the real Planner as Mia and the Prototype at the same body width and mode, and compares the module's markup in both shadow roots after it settles: the element tree, classes, `data-*` attributes, `hidden` and text, with the server's ids (the space id, the people's keys, versions) written back as the sample's placeholders. The first difference is reported with its path and both sides. At 1280 light, 700 and a real 390 window. This replaces part (1) and catches what it could not: a new slot, a changed hide rule, a wrong answer from the sample host.
2. **Same answers.** For each call the Prototype's Planner made, where the call reads data, the sample host's answer equals the real `handlers` answer for the same seed (placeholders resolved). This names the `derived` entry that is out of date.
3. **Nothing unknown, nothing sent.** The Prototype records every call: one answered "Not in the Prototype: <call>" (unknown) fails; one of the listed "Not in the Prototype." calls during the first draw is reported. Any request from the Prototype tab outside the list above fails, and so does any error in its console.
4. **Kept from today:** (2) columns, (3) the joint, (4) phone taps, on the real Planner (question 10), and (5) container not window, on the Prototype.
5. **No copies** (no browser): no file under `public/design-system/` outside `legacy/` holds a `data-slot=` attribute or a `<template id="tpl-`, and none imports or fetches from `modules/`. The sample data file holds nothing that looks like a key, a token or an email address. This replaces part (6) and keeps a copy from coming back.
6. With no Chromium it says SKIPPED and exits 0 (a skip, never a pass), and fails when `CI` is set, as now.

## Risks

- **The answers drift.** The sample host is a second source for the answers' shapes. Check parts 1 and 2 compare it with the real server on every `npm run check`; a difference fails with the call's name.
- **The module learns a new call.** It fails in the Prototype as "Not in the Prototype: <call>" and fails the check; adding the answer is part of the change that added the call.
- **Real data.** The Prototype is open to anyone. The sample host makes no `/api/` request (checked), the route reads only `modules/` and `templates/`, never `DATA_DIR`, and has no write method. On a single-environment install a signed-in person who opens the Prototype has a session in the same browser; the check's request list is what proves the Prototype does not use it.
- **The module's own power.** A bundled module in the page runs with the page's power (`module-host.js` says so). In the Prototype that page has no data to reach, and the check fails on any request outside the list.
- **Module source on the product host.** The route shows a bundled module's built page to anyone. It is the same code every signed-in person's browser receives, and no bundled module holds a secret (nothing checks that today; `tools/check-secrets.mjs` tests the server's answers, not files). Question 9.
- **Check time.** The seed boot stays the bulk of the 25 to 46 seconds; the markup comparison adds a few seconds. Question 11.
