# Modules Architecture

**Audience:** developers changing how Collaborator installs and stores modules.

What an admin does with modules is [userguide-modules](../userguides/userguide-modules.md), and the
routes are [api-modules](../api/api-modules.md). This document is what you can only learn from
`server/modules.js`.

## Model

A module is front-end only. Nothing in a zip is ever run by the server: every file type is allowlisted,
and the zip is read entirely in memory against hard limits before a single byte is written. A module
runs in a sandboxed frame and reaches Collaborator only through a host bridge, so accepting a zip from someone
else is bounded by that sandbox and by the admin's approval, not by trust in the author.

## On disk

Under `DATA_DIR/modules`:

```
registry.json                     what is installed and its state
<id>/versions/<version>/...       the module's files, one folder per version
<id>/data/                        the module's own data, kept across upgrades
```

`registry.json` is written by writing a temporary file and renaming it. Each entry holds the active
`version`, the list of installed `versions`, `enabled`, `allSpaces`, `spaces` (`allRooms` and `rooms` before the Names migration's `names-spaces` part), and `approved`, which is
the permissions and hooks the admin agreed to. The manifest is read from the version's own
`module.json` on demand, so the registry cannot drift from the files.

## Display names, icons and words

What a person reads a module called is its **display name** in this environment
(plan-environment-templates, step 2). `store.moduleDisplay(id)` in `server/store.js` resolves it for any module,
installed, bundled or built in: the owner's own (`settings.moduleNames`, `settings.moduleIcons`), else the
template's (step 3), else null, meaning the manifest's own `name` and `icon`. An icon counts only while it can be
drawn (`displayIconIds()`: the environment's plain solid icons, `fa-solid fa-<id>`, and every installed or built-in
module's own icon); one that can't be drawn now is kept as the owner's (`ownDisplayIcon`) and the next one down is
shown. `buildEnvironment()` hands this to the module manager as `modules.displayOf`, and `modules.shownName()`
is what every sentence, notification and activity line uses. `GET /api/modules` keeps `name` and `icon` as the
manifest's and adds `displayName`, `displayIcon`, `ownDisplayName` and `ownDisplayIcon`; the module's own page
gets the display name and icon as `info.module`. The top bar names no module, so a change needs no redraw there.
A module's display name replaces its name only, never a widget's own title. On Manage the owner edits them on the Template tab (one row per module, `#template-module-<id>`); each Modules card shows only "Shown as" with a **Change** link to that row.

The text in a manifest that people read (description, widget title, permission labels, setting labels, help and
options, event and action labels, kind names) may carry the environment's word placeholders (`{space}`,
`{a space}`, ...), and is filled from the environment's words wherever it is sent, so it reads in the owner's
words (see "Words" in [architecture-overview](architecture-overview.md)).

## Reading the zip

`readZip` in `server/modules.js` uses `yauzl` on the uploaded buffer and builds a map of file name to
bytes. It refuses, with a message the admin sees:

- an unsafe path (the library already rejects `..` and absolute paths), or control characters in a name;
- a symbolic link, detected from the entry's Unix mode bits;
- any extension not on the allowlist;
- more than 500 files, a file over 10 MB, or more than 40 MB in total.

Sizes are checked twice: from the entry header before reading, and again on the bytes actually
streamed, because a header can lie. A zip made from a folder, with everything inside one top-level
folder, has that folder stripped when `module.json` is found inside it.

## Manifest validation

`cleanManifest` builds a fresh object from only the fields it knows, so unknown fields cannot reach the
registry, and it checks that each surface entry exists in the zip. It returns the cleaned manifest or
throws a `ModuleError`, which is a `StoreError` and so is turned into a JSON error by the server's
error handler.

Since step 5c of the [Names plan](../plans/plan-names.md), `oldNameIn()` checks the raw manifest first: a module
`scope` of `server` or `room`, a setting's scope, `install.settingsFrom: "server"`, or a permission default keyed
`user` refuses the upload with one sentence naming the new word. The stored `module.json` is the author's
original, so an installed version in the old names is kept and read with `manifest.outdated` set: it counts as
off whatever the registry says (`enabledAll()` and the run routes skip it), `GET /api/modules` shows `outdated`,
`outdatedWhy` and `outdatedVersions`, turning it on or rolling back to such a version answers 409, and
`needsUpdateFor()` keeps off every module that requires one (409 "`<Name>` needs `<Req>`, which needs an update from
its author."). More generally, a module runs only while everything it requires is running, at any depth; the
owner's on or off is kept, so it comes back by itself when its requirement does, and `missing` and `needsUpdate`
on its card say why it isn't running. The registry keeps the owner's own on or off, so an update that fixes the manifest runs as before.
Modules that ship with Collaborator are updated to their new copies on start (see
[architecture-environments](architecture-environments.md), "Bundled modules built for an older version").

A permission may name `replaces`, the key it had in an earlier version; each role's choice for that key in
`settings.roles` is carried over once, at start and after any install, so renaming a permission keeps what owners
chose. Two permissions naming the same old key are refused: `module.json: permission "<second>" replaces "<old>",
which permission "<first>" already replaces`.

## Modules that ship with Collaborator

`server/module-build.js` builds a module's zip from its source folder (`modules/<id>/module.json` and `src/`), inlining the CSS and JS into the pages; `tools/build-module.mjs` uses it to write a zip, and the server uses it to offer the modules in the deployment's own `modules/` folder. `GET /api/modules` compares each bundled version with the installed one (`update` is true when it is newer and not already kept), and `POST /api/modules/bundled/:id/install` builds the zip in memory and passes it to `install()`, so a bundled install or update goes through the same validation, version keeping and approval as an upload: an update that asks for something new is left disabled until approved. An installed copy is updated only when the bundled version is newer, so any change to a bundled module needs a version bump; `tools/check-module-versions.mjs` enforces it against a recorded fingerprint. Only folders directly under `modules/` whose `module.json` id matches the folder name and that have a `src/` are offered, by id, so a request cannot name a path.

## Install, upgrade and rollback

**Stored keys a module renamed.** A manifest's `storage.renamed` (`[{ from, to }]`, key prefixes) makes the server
keep the module's stored keys matching the version running: `server/module-data.js` renames keys starting with
`from` to `to` in every scope: a rename is in effect for every version from the one that introduced it onward, even if later versions stop listing it. While it is in effect, keys still under the old prefix are moved on every start, install, update and rollback; switching to a version older than the one that introduced it moves the keys back (the newest rename first) and drops the record. The registry records each as `renamed: [{ from, to, version, at, kept }]`. A key whose new name is already taken is never overwritten: both are kept (`kept`). The log and the activity list note only keys actually moved and new conflicts. `cleanStorage()` in `server/modules.js` refuses a list that repeats a
`from`, overlaps or would move keys back.

**Bundled modules keep up with the server.** On each start, every module that came with this deployment is updated
to the version the server ships whenever the update asks for nothing new to approve; one that asks for more waits
for an owner, and the installed version keeps running meanwhile. Uploaded modules are never touched. (Since step 7;
before, only an outdated bundled module was updated on start, see [architecture-environments](architecture-environments.md).)

Files are written to a staging folder next to the final location and moved into place with a single
rename, so a failure never leaves a half-installed version. A new module is created disabled. An
upgrade keeps `enabled`, `allSpaces` and `spaces`, then compares what the new manifest asks for with
`approved`; anything new turns `enabled` off. Rollback changes only the active `version` and applies
the same check. After each install, only the newest three versions are kept, never removing the active
one.

## Approval

`pendingFor` returns the permissions, hooks and `refs.consumes` entries in the active manifest that are not in `approved`.
Enabling copies the whole current set into `approved`. That is why an upgrade can quietly gain a
capability only if the admin approves it.

## Uninstall

Removes the `versions` folder and the registry entry. The `data` folder is removed only when asked, so
that reinstalling the same `id` finds its data again.

## Running a module

What an admin does is [userguide-modules](../userguides/userguide-modules.md); what a module author sees is [api-module-sdk](../api/api-module-sdk.md). This is how the pieces fit.

```
 module frame (sandboxed)  <--postMessage-->  host page (module-host.js)  <--HTTP + SSE-->  server
   public/sdk/host.js                          module.js or canvas.js               index.js, modules.js,
                                                                                            module-data.js, module-hooks.js
```

### The dashboard

The spaces page is a `.home` grid: a sticky sidebar, `#dashboard`, on the left and `.home-main` on the right (a `#whos-around` strip, then the space cards); on a phone one column with the main part first. `public/dashboard.js` fills the sidebar with a card for each module with a `surfaces.widget`, listed by `GET /api/modules/widgets` in the order the manifests ask for. A widget is mounted exactly as a module page is (`mountModule` with `scope: 'environment'`, in the page for a bundled module and in a sandboxed frame otherwise), so it uses the same SDK and the same reads across the viewer's spaces (`spaces-data`, checked against the module's read permission in each space). Collaborator knows nothing of what a widget shows. An object a widget opens (`objects.open`) in a space takes the person into that space with only that module open on the canvas: `openInSpace` in `public/space.js` asks the canvas manager (`requestOpen` in `public/canvas.js`) to open just that module and hand it the pointer on the next restore, then joins (or shows the canvas when already in that space). That one-off layout is not remembered as the space's layout until the person opens or closes a module themselves. An object outside a space goes to the module's page, given the pointer in the address (`openRef` in `dashboard.js`); the card's heading links to the module's own page. While the module is part of a shown destination, the heading, `host.page.open` and the tile's own module's objects go to the destination instead (`tileRefTarget()`; see [architecture-navigation](architecture-navigation.md), "Module pages"), and `{ newTab }` on either opens a new tab. Who is around (Collaborator's own, from `/api/presence`) is drawn into the strip. A widget can ask for its module's page at a place in it with `host.page.open(hash)` (the host's `page.open`, answered only by the dashboard), which goes to `/modules/<id>#hash`; the module page hands the hash to the module (`pagehash`, `host.page.onHash`), as it does a pointer. The sidebar stays hidden until it has a card; a guest has no dashboard. A module's build (`server/module-build.js`) writes the widget entry from `src/<id>-widget.*`, and inlines `src/<id>-lib.js`, then any `src/<id>-lib-*.js` in name order, wherever a script has `/*__LIB__*/` (and any `src/<id>-lib-*.css` ahead of the page's own CSS, for a library that brings a stylesheet). A shared library with no page in it can be run on its own by a check (`tools/check-travel.mjs` does this for the Travel module's model and plan).

### Shared tools

The SDK carries what more than one module needs (the date picker, the action menu, the drop decision `host.objects.dropMenu` -- what dropping one module's object on another can do, one menu for every module, filled from what the modules around declare -- and small helpers in `host.util`), so modules stay small and look and behave alike. The picker and menu draw their elements inside the module's own root, positioned by the page's coordinates, and add their styles once to that root in the theme's colours, so they work in a frame and in the page. The rule for the SDK: when a second module needs something a first one wrote for itself, it moves into the SDK and the first module uses it from there.

### Settings

`server/module-settings.js` keeps what people chose for the settings a module declares, in `DATA_DIR/modules/settings.json`: `{ environment, spaces, people }` (it was `{ server, rooms, people }`), one bucket for the environment, one per space and one per person, each holding a module's values. The manifest's definitions are cleaned in `cleanSettings` (`server/modules.js`) and every value is checked against its definition on the way in. `GET /api/modules/:id/settings/values` gives a module the values that apply to the viewer (the environment's, the space's and the person's, defaults filled in), and a change goes out on the shared stream as `settings` so open modules read them again. Who may change what is decided in `settingsPlace` in `server/index.js`: an owner for the environment's, an owner or a member ticked as a moderator in that space for the space's, and anyone for their own. The forms are drawn by `public/module-settings.js` (the Modules tab for the environment's, the space's page for an owner, `/module-settings?space=` for a space's moderators, the profile page for a person's own). Changes to environment and space settings add a line to the activity list; a person's own do not.

### Run modes

`runModeOf` in `server/modules.js` decides how a module runs: the admin's explicit choice, else the page for a module installed from those that ship with Collaborator (`source: 'bundled'`), else a sandboxed frame. Switching an uploaded module to the page needs `acceptRisk`, and the server records when. The frame path is described below. For the page, `/m/<id>/<version>/<entry>?part=css|body|js` returns the style, the markup and the script of the module's single HTML file, and answers 403 unless the module runs in the page. `startInPage` in `public/module-host.js` attaches a shadow root to the module's container, injects the base stylesheet (scoped) and the module's style and markup, and loads its script as an external script carrying the SDK instance (the space page's content security policy forbids inline script). The SDK is the same code (`createHost`); over a frame it talks by `postMessage`, in the page the host calls its handlers directly. A module in the page can bypass the SDK, so the approved-permissions list, which the server checks per call, stops being a limit on it; that is why the choice is the admin's, behind a warning. The Maps module shows how a large front-end library rides in a bundled module: MapLibre GL JS and the PMTiles reader are `src/maps-lib-*` files inlined into its page, the map's worker starts from a blob (the page policy allows `worker-src blob:`), the map file is read by range from `GET /api/modules/:id/files/:name` (the operator's file in `DATA_DIR/modules/<id>/<folder>/`, the folder its `file` setting names; installing, updating and uninstalling never delete it, even when the module's data is wiped, chosen by a `file` setting), and the label glyphs are static files under `public/maps-glyphs/`. `GET /api/modules/activity` (admin) lists what modules have done recently, shown on the Modules tab; the list (300 lines) is written to `DATA_DIR/modules/activity.json` a few seconds after a change and when the server stops. `server/module-limits.js` rate limits what goes through the API per module and person (saves, events, actions, schedules, notifications, searches, uploads, AI requests and object checks) with a sliding minute; it limits only what passes through Collaborator, so it is not a boundary for a module running in the page.

### The frame

A module page is served from `/m/<id>/<version>/<file>` by `server/index.js`. Only the active version of an enabled module is served, and the path is checked to stay inside the version folder. The response carries `Content-Security-Policy: sandbox allow-scripts allow-forms; default-src 'none'; script-src 'self' 'unsafe-inline'; ...; connect-src 'none'; form-action 'none'`, so even when opened directly it has an opaque origin, no cookies, and no network beyond loading its own files. The host also sets `sandbox="allow-scripts allow-forms"` on the iframe. `allow-forms` is there because a sandboxed frame without it swallows a form's `submit` event, so a module's Save button appears to do nothing; `form-action 'none'` means nothing can actually be submitted.

HTML pages are rewritten on the way out: the SDK and the base stylesheet are injected inline right after `<head>`, unless the page already includes `/sdk/host.js` (the SDK) or carries `<meta name="sdk-base" content="none">` (the base styles). Inline injection means a module needs no subresources at all, so it works wherever a sandboxed frame may not load its own files.

### The bridge

`public/sdk/host.js` (in the frame) and `public/module-host.js` (in the hosting page) speak a small `postMessage` protocol: the frame sends `{ host: 1, id, method, params }`, the host answers `{ host: 1, id, result | error }`, and pushes `{ host: 1, event, data }`. The host answers only messages whose `source` is its own frame's window (the frame's origin is opaque, so the origin cannot be checked). In the other direction each frame gets a random secret in its address (`?tk=`), every message the host sends carries it, and the SDK ignores messages without it; who sent a message cannot be the check, because when the call is popped out the host code runs in a different window from the frame's parent. Each method becomes an authenticated HTTP request on the frame's behalf; the frame never holds a session.

A module's action bar rides the same bridge: `bar.set` gives the host a list of buttons, the host draws them into the bar element for that surface (a cell in the canvas grid when docked, a strip elsewhere) and sends each click back as a `bar` event. The host validates the items (up to six, short labels, icon names limited to Font Awesome names).

The host passes the theme in `hello` as a set of CSS custom properties read from the page's computed style, and the SDK sets them on the frame's `:root`.

### Who may do what

Every runtime route calls `moduleAccess` in `server/index.js`, which resolves the module (it must be enabled), the caller (a signed-in user, or a guest with a space's guest link token), the scope, and for a space scope checks that the module is on for that space and the caller is in it. That holds for a module's environment page writing into one of the caller's spaces (`scope=space&space=<id>`, the SDK's `{ space }`): `scopeOf()` in `public/module-host.js` (the pure `placeOf()`) only shapes the request, letting an environment mount name a space and keeping a space mount to its own, and the server applies the same check as for a page in that space. `GET /api/modules/:id/spaces-data` gives each space `write`, the module's `write` permission there, so an environment page offers adding only where it may (the Calendar's, To-do's and Places' **Where**). It then checks the module's `access` permission through `store.spacePermissions`, so the Moderator grant for a space applies to modules too. The module's permissions are added to the Roles grid at run time: `ModuleManager.permissionList()` supplies `module.<id>.<key>` entries, `store.extraPermissions` hands them to `Store.roleSet`, and `store.allPermissions()` feeds the Roles grid.

### Data

`server/module-data.js` keeps a key-value store per module and scope: `data/modules/<id>/data/environment.json` and `space-<id>.json` (named `server.json` and `room-<id>.json` before the Names migration's `names-spaces` part, which moves them; uploads likewise sit under `uploads/environment/` and `uploads/space-<id>/`). Inside the host a scope is a key: `environment`, `space:<id>` or `person:<key>`. Each scope loads once into memory and is rewritten whole on a change. Every key carries a version; a write that names a stale version gets a conflict carrying the current value. The 5 MB cap is checked against the module's total data on disk. Each write emits a `change` event.

### Personal data

A module that declares the `person` scope keeps data per person (`DATA_DIR/modules/<id>/data/person-<user key>.json`, with the same versions and 5 MB cap as a space's). The route never takes a person from the request: `moduleAccess` names the store from who is signed in (`person:<key>`), so one person cannot ask for another's, and an administrator is a person like any other here. Change events for it are sent only on that person's own streams (`place()` in the modules stream checks the key). Pointers carry `scope: 'person'` and resolve against the viewer's own store, so a pointer someone else holds shows as gone; links (`setLinks`) refuse personal objects on both sides, so the shared link store never learns of them. Guests have no personal data.

### Live changes

`GET /api/modules/stream` is one server-sent event stream for every module on a page. It subscribes to `change` events from the data store and `fire` events from the scheduler and writes them as `change` and `schedule` events, each labelled with its module and a scope (`space`, `environment` and `person` for a space's modules, `environment`, `person` and `spaces` for a module's environment page) and a `spaceId`, checked against what the viewer may read. `public/module-host.js` shares one stream per space and page between all its frames and forwards each event into the right one. This matters because browsers allow only about six long-lived connections to one host over HTTP/1.1: a stream per module (two for a module on the canvas) used them all with three modules open, and every other request, including a frame's first call to the host, waited forever, which the frame reported as the host not answering. `GET /api/modules/:id/events` remains for a single module and scope.

### Objects

**The principle.** Collaborator is the conduit and the transport; it does not know what a task, an event or a poll is, and no code in it, or in one module, is written for a particular other module. Everything that lets modules work together is declared by the modules (what they share, what they can open, what they show links to, what they want to link to) and carried out by generic routes that read those declarations. If a change to Collaborator names a module, or a module lists other modules by name in its code, the design has slipped. A module installed tomorrow takes part by declaring, and the modules around it need no change: linking a to-do to objects of a module written after it works because the To-do consumes `"*"` and asks Collaborator what it may link to.

Modules cannot read each other's data, and pointers to objects are the single, declared exception. The stored `module.json` is the author's original, so `cleanRefs` in `server/modules.js` normalises `refs` when a manifest is installed and again whenever one is read (`manifestOf`). A producing module maps a kind to a stored key (`event:{id}`) and to summary fields (`refs.produces[].summary`; `card` before step 7 of the Names plan, now refused); a consuming module lists `module:kind` entries an admin must approve. Because modules are front-end only there is no provider code to ask, so the summary is built by the server from the provider's stored value, and only the named fields are copied.

The routes in `server/index.js` (`/api/objects/resolve`, `/api/objects/search`, and one summary by address; `/api/refs/*` before step 7, now 404) all pass through `refScope`, which checks, in order: the asking module is named, the provider is enabled and produces that kind, the asker declared and was approved for `provider:kind`, the scope exists (a space the viewer may open, or the environment for a signed-in person), and the viewer holds the provider's `read` permission there. Missing or refused objects come back as an error per pointer, never a stack trace or a partial record. `GET /api/objects/search` reads one scope, or with `scope=spaces` each space the viewer is a member of in turn through `refScope` (so each provider only where it is on and readable), each pointer carrying its space; `has=place` keeps the summaries with a place and raises the cap from 50 to 1,000, for a map that needs every pin. The host (`public/module-host.js`) always sends the frame's own module id as `from`; that is a consistency check rather than a security boundary, since the viewer is the one authorised, and their own permissions in the provider are what decide the answer.

A consumer stores only `{ module, kind, id, scope, space? }` (`scope` is `environment`, `space` or `person`) and resolves it each time it draws. Two more conduits build on the same pointers. **Opening**: `objects.open` asks the page to show an object in the module that owns it (`openRef` in `public/canvas.js` opens it on a space's canvas; `public/module.js` goes to its page), and delivers an `objectopen` event, which the owner's `host.objects.onOpen` turns into showing the object; nothing is known about the object. **Links**: a module tells Collaborator what its own objects point at (`POST /api/objects/links`), which `server/module-links.js` keeps as pairs of pointers, never content; the module that owns an object marked `backlinks` can then ask what points at it, and every answer is resolved through the source module's own read permission for that viewer, so a link is only as visible as its source. A change is announced to the affected modules as a `links` event on the shared stream. Dragging is brokered by the host and driven by the pointer, because the browser's drag and drop does not reliably deliver a drag from one sandboxed frame into another. The source frame's SDK (`host.objects.draggable`) follows the pointer (captured from the press, so it is followed outside the frame too) and tells the host where it is in the frame's own coordinates (`objects.ptrStart`, `ptrMove`, `ptrDrop`); `ptrBegin`, `ptrMove` and `ptrDrop` in `public/module-host.js` convert to the page's, find the module frame under the pointer, draw the label at the pointer, and forward `over`, `leave` and `drop` to that frame in its coordinates (the `objectdrag` events that `host.objects.dropTarget` turns into callbacks). It only works between frames in one window. An earlier design put transparent layers over the other frames for a native drag; that path (`objects.dragStart`) is still there for a native drag, and the older text follows.

Native drag, for reference:  `host.objects.drag` sets the pointer on the drag (`application/x-host-object`, carrying `{ ref, summary }`, for a drop into a frame in another window) and tells the host (`objects.dragStart`, checked for shape). `beginDrag` in `public/module-host.js` then puts a transparent layer over every other module frame on the page; the layers are in the host's own page, so they receive the native drag, and forward `over`, `leave` and `drop` to the frame beneath in that frame's coordinates (`objectdrag` events, which the SDK's `objects.dropTarget` turns into callbacks). The layers come down on the source's `dragend`, on a drop, on a click, or after 20 seconds, so a module cannot leave them up. A receiver validates the pointer's shape and resolves it, so a forged drag reveals nothing.

### Keeping links true

`server/object-sync.js` keeps a pointer true after its object changes, with no page open ([plan-linked-objects](../plans/plan-linked-objects.md), [plan-plan-calendar-sync](../plans/plan-plan-calendar-sync.md)). The `PUT` and `DELETE /api/modules/:id/data/:key` routes read the old value, write, and then call `afterWrite` with the old and new values, the writer and the writer's time zone (`tz`, sent by `public/module-host.js`; `TZ`, then UTC, when it is missing or unknown). `afterWrite` maps the key to a produced kind and does three things. It tells the modules that hold a link to the object (`refchange` on the shared stream, only to the frames of those modules the viewer may see, and only when the summary changed or the object went). It acts on each holder whose kind declares `holds`: removes or marks it on delete, copies the title, and moves its day with the object unless it is pinned. And it keeps dated twins: a kind with `mirror: "out"` gets one twin in each kind with `mirror: "in"` that is on in the same space and that the sender was approved to link to, and an edit on either side writes the mapped title, day and time into the other. Converting between a day and an instant uses the writer's time zone.

The server keeps the pairs, not the modules. A pair is a link entry in `server/module-links.js` with `pair: "active"` or `"detached"` (the twin was deleted; the sender keeps its day until that day changes). `set()` leaves pair entries alone, so a module's `setLinks` never removes one, and `to()` and `from()` include them, so backlinks and "Used by N." count them. The manifests declare what a kind does (`holds`, `dated`, `mirror`, `create`, checked in `cleanRefs` in `server/modules.js`), so no module names another. Loops cannot start: every write this file makes goes straight to the data store and never back through `afterWrite`, and a write happens only when a value differs. Those writes do not count toward the write limit; a full store (413) skips a twin until the next change.

On every start, `backfill()` gives a twin to each space object of a sending kind that has a day, holds no pointer and has no pair, in the server's time zone. `server/index.js` runs it once in a single-environment install and once per environment in a hosted one, as the server begins listening. Because a pair (active or detached) is the record, only the first start after a kind declares `mirror: "out"` makes anything. `tools/check-links.mjs` covers the change events, held pointers, pairs and a single-install restart, with test modules declared inside the check.

### Calendar feeds

`GET /feed/<token>.ics` in `server/index.js` gives a person's calendar app the objects of every kind marked `"feed": true` (with `"dated"`, checked in `cleanRefs`) that they may read, as an iCalendar file written by `server/ics.js` (`readDated()` reads a stored value by its `dated` mapping, repeats included; `buildCalendar()` writes it in the server's `TZ`). The kinds are found from the manifests, so nothing names the Calendar. Each read checks the person's permissions as they are then: the environment's own data, and each space they are a member of (the `spaces-data` rule). The token is shown once and stored as its SHA-256 on the user (`store.setCalendarFeed()`, `userByFeedHash()`); reads are limited to 30 a minute per address, and `readAt` is written at most hourly. The routes are in [api-modules](../api/api-modules.md), "Calendar feeds"; `tools/check-feed.mjs` holds them.

### Other calendars

A person may add up to five private calendar addresses on their profile (`/api/me/external-calendars`). `server/external-calendars.js` (one per environment, `server/environment.js`) reads them through the private-address guard in `server/link-preview.js` (https only, 5 MB, 15 seconds; IPv6 literals and names resolving to private or special IPv6 ranges are refused, as for link previews and Research), parses them with `server/ics-read.js` (repeats expanded, 30 days back to 180 ahead, 2,000 per calendar; a file needing more than 200,000 repeat periods to expand (or, as a backstop, 1,500 ms) is refused whole as too complex), and keeps the events in memory only, reading again every 30 minutes for someone seen in 14 days and after a restart on first use. The addresses are sealed on the user record with the secrets key (`auth.encryptSecret`) and opened only to read them or show their host. A module reaches the events only through the `external` hook, which an owner approves, and only the signed-in person's own (`GET /api/modules/:id/external-events`, `host.external.events`); a read tells that person's pages with an `external` stream event. They never show inside a space: not on its canvas, a window popped out of it, a keyed page, or a page opened over a call, `/calendar` included. Nothing names a provider or a module. The contract is in [api-modules](../api/api-modules.md), "Other calendars"; `tools/check-external-calendars.mjs` holds it.

### The objects format

An AI writes objects in one fixed shape, whether it is the Assistant's own AI or another AI a person researched in, and one checker reads both. `server/object-format.js` owns that shape: the icons and kinds, the field caps (title 80, content 6000, five tags, five `http` or `https` links), `cleanObject` (the checker), `objectRule` (the prompt text), `instructions` (the text a person gives another AI), `schema` (a JSON schema) and `readObjects` (finding objects in a paste or a file). `server/ai.js` takes its icons, kinds, checker and rule from there: its `SUMMARY_RULE` (the rule for `/ai`'s answers) is `objectRule` called with the `objects` fence and the noun "object", and the published instructions are the same function called with the same fence, this environment's word for object and a limit of 50, so the two cannot drift. `parseSummaries` reads blocks labelled `objects` and, for a model that labels its block loosely, `summary`, `json` or nothing. `tools/check-object-format.mjs` checks that both ask for one array in one `objects` block and that the rule never says "card".

**Named by kind.** The file is `<something>.objects.json`, `{ "format": "objects", "formatVersion": 1, "objects": [...] }`, and the block is fenced ```` ```objects ````. The theme and template files carry the same marker pair with their own kind (see [architecture-overview](architecture-overview.md), "Themes", and [architecture-environments](architecture-environments.md), "Template files"). `server/file-format.js` is the one rule for all three: `stamp(kind)` writes the pair, and `readMarker(file, kind)` answers `ok`, `newer`, `old` or `not`, so no reader repeats it. Until 2026-09-30 the formats were named after the product; Thomas decided they are named by kind so the product's name can change without touching a format ([plan-kind-names](../plans/plan-kind-names.md)). Old files and answers are refused with a sentence saying what to do, never read: an old marker is recognised by its exact past name, built from `PAST_BLOCK_LABELS` (the two labels ever published) and the kind, so a real object with a key such as `relatedObjects` is still an object; and a paste with a block fenced with a past label, wherever the fence line sits (indented, in a list or a quote), is refused whole, even beside an `objects` block, so nothing is imported by halves. `PAST_BLOCK_LABELS` is the only place the old labels are written in the code and must never grow. The loose reading (any JSON object with a `title`) still rescues a paste that lost its fences, and is the only way a ```` ```card ```` block is read now. The exact rules are in [api-modules](../api/api-modules.md), "The objects format".

Reading costs no AI and stores nothing, so it is a conduit, not an AI feature. `GET /api/objects/format` and `/format/schema` publish the format to anyone signed in or holding a guest link. `GET` and `POST /api/modules/:id/objects/check` answer, for the asking module in its place, whether this person may bring objects in and what a paste or file holds. The rule is the module's own `write` permission, never a guest, and not in a space with AI turned off; no AI service, `useAi` or new module permission, because a new permission would turn the module off on every install until an owner approved it again, and what is finally kept is limited anyway by the destination module's own write permission, since keeping goes through actions. The route has its own body parsers (`text/plain`, or `application/octet-stream` decoded as `public/file-text.js` does) with a 256 KB cap and its own 413 branch in the error handler, and a `check` rate limit of 20 a minute in `server/module-limits.js`. An object read this way is always marked `basis: "imported"` and loses its `sources`, since another AI's item numbers mean nothing here. The contract is in [api-modules](../api/api-modules.md), "The objects format".

Nothing here keeps an object. A module that brings objects in decides where they go; the Assistant, the only one today, keeps them through the action bus exactly as it keeps its own answers (a suggestion-shaped action for an object with a `kind`, else a note-shaped one), which reaches Research and the Planner. So long research fits, a `text` action input is kept up to 8000 characters (it was 1000), and the Planner keeps notes up to 8000. Honouring more destinations (To-do, Calendar) through a generic conduit, and a direct connection for AI apps after #64, are planned in [plan-research-import](../plans/plan-research-import.md).

### Events and actions

`server/module-bus.js` keeps the two other conduits. An **event** (`POST /api/bus/publish`) must be one the publishing module declared, from a person who can write to that module in that place, with an optional pointer that can only be to the module's own objects there; it is stored (500 kept, 14 days) and announced on the shared stream (`GET /api/modules/stream`) as a `bus` event that names the modules that may hear it: those that declared and were approved for it and that this viewer can see in that place. The host delivers it only to those frames. A subscriber that was not open catches up from a cursor the SDK keeps in the module's own data (`GET /api/bus/events?after=`); a module hears nothing from before its first subscribe. An **action** (`POST /api/bus/actions/request`) is checked in the order asking module approved for it, the person can do the thing themselves (write access to the provider), the provider declared it; its input is validated against the declared field types (a `string` cut at 200 characters, a `text` at 8000) and only those fields are stored, then it waits in the provider's queue. The provider's frames are told (`action` on the stream); each asks to `claim` it and only one is given it (a claim not completed within a minute can be taken again), carries it out under the rules of whoever has the module open, and reports `complete`. Modules run no code here, so a request with no provider page open simply waits (seven days) for a person to open one. **Actions in the object's own place.** An environment page (a destination's part) may ask for an action on one of the provider's own objects in a space, such as setting a space's task's due date from Calendar. The request is checked by the viewer's right to change the provider in that object's space, not at environment level (`actionObjectSpace()` and `takesOwnObject()` in `server/index.js`, for an action whose input takes a `ref:<provider>:<kind>`); it still waits at environment level, where the asking and providing parts are, and records the space (`space` on the request in `module-bus.js`), so `pending`, `claim` and `complete` let only someone who may change the provider there take it. `GET /api/bus/actions?ref=` lists the actions by the same rule for the object a drop is about. A page in a space keeps its own place, as before. Nothing in `module-bus.js` or its routes knows what an event or an action means. A `ref` input field can be typed `ref:module:kind` (checked in `cleanBus` and enforced in `busInput`), and `GET /api/bus/actions?accepts=module:kind` lists the actions that take that kind, which is how a module receiving a drop learns what can be done with the object without knowing where it came from. Events may declare the data they carry (`cleanBus` keeps up to six typed fields), and `GET /api/objects/kinds` lists, for each kind a module may link to, the events that kind reports and their data; that is how a following module offers rules without naming the module it follows. The drop menu is drawn by the SDK (`host.actions.pick`) inside the module's own root, at the point of the drop, so it works the same in a frame and in the page; the choices are the receiving module's own plus the actions Collaborator lists, filled from what the receiver has.

### Commands

`cleanCommands` in `server/modules.js` checks a manifest's `commands` against its own `actions.provides` (each must name a `local` action that takes `text`; `ai` is reserved), at install and again when the registry loads. `GET /api/modules/for-space` hands them to the page, and `POST /api/spaces/:id/command` in `server/index.js` finds the one named and requests its action on the bus, so Chat never names a module. The contract is in [api-modules](../api/api-modules.md); the reasons in [plan-one-input](../plans/plan-one-input.md).

### Hooks

`server/module-hooks.js` holds schedules and notifications. Schedules persist to `data/modules/schedules.json` and a ten-second timer fires what is due: it delivers the schedule's notification, if any, and emits `fire`. A schedule more than six hours late (the server was off) is dropped. The timer's tick runs inside its environment (`runIn`, which `server/index.js` sets to that environment's context), and each listener of `fire` and `notification` is called on its own (`tell()`): one that throws is logged, the rest still hear, and nothing stored is undone, so a schedule can never stop the server. A notification is stored before listeners are told. The stream routes register their listeners with `listenIn()`, so an event from the timer, or from a region cut, is handled in the listener's own environment. `tools/check-hooks.mjs` holds this. A repeating schedule is put back for its next time as it fires (`requeue`), computed in the schedule's time zone with `Intl` so the wall-clock time survives daylight saving changes; it skips times the server slept through and stops after `until`. Notifications persist per person in `notifications.json`, capped at 50, and are emitted as `notification` events on `GET /api/notifications/stream`. A notification reaches only people who pass the module's `read` permission for that place, which `resolveRecipients` in `server/index.js` checks. A schedule set by the module while an admin approved the hook is the only way a module causes anything to happen on its own.

### Where modules show

- **Environment pages.** A module's environment page is reached from its tile's heading on home, or at `/modules/<id>`; the top bar has no entry for module pages (plan-primary-nav, decisions 30 and 31). Opened from the space page they open in the in-page overlay, so the call keeps running.
- **Environment page.** `/modules/<id>` serves `public/module.html`, whose script (`public/module.js`) mounts the module in a full-height frame.
- **Destinations.** A destination is a host page of its own in the top bar (Calendar at `/calendar`, Map at `/map`), made of the parts modules declare in `surfaces.destination`: one `main` and any number of panels per destination, each an entry of the module's own, mounted at environment scope ([plan-calendar-destination](../plans/plan-calendar-destination.md), [plan-map-destination](../plans/plan-map-destination.md)). The host names the destinations, never the modules: `server/destinations.js` holds the list (`DESTINATIONS`: id, the environment option that shows it, its page, and whether it needs its main module to have a file), picks the `main` (the bundled module that declares it, else the first by id), orders the panels and decides who sees what; `cleanDestinationParts()` in `server/modules.js` checks the manifest field (a destination the host knows, at most one `main` and one `panel` per destination, two parts in all, the `environment` scope). So the Calendar is a destination because the Calendar module declares its `main`, and a module written later can offer a panel with no change to Collaborator. While a destination is shown, the environment page of each module that is part of it redirects there and its tile's heading leads there (`destinationPathOf()` in `server/index.js`). The page and its state are in [architecture-navigation](architecture-navigation.md), "Destinations"; the routes in [api-modules](../api/api-modules.md), "Destinations".
- **Modules on the canvas.** `public/canvas.js` drives the Layout button in the space bar and its panel's Show section (the menu lists the conference, the chat and the modules, opens under the button, and is the single way to open or close a module (when the menu element carries the class `subnav-modules`, it is an always-visible row of buttons in the space bar: `public/canvas.js` then never hides or positions it and only keeps its buttons current); the chat's unread count shows on the button) and opens each module in one of three ways. **Docked**: a column of the canvas's grid after the video and the chat (see [architecture-canvas](architecture-canvas.md)), with a header the host draws at the shared height and a drag handle on its left edge. **Floating**: in a layer on the main page, dragged by its title and resized by its corner. **Popped out**: its own window, which is `/modules/<id>?space=<space id>&popout=1` (the same page an environment page uses, in the space's scope, with no header; the old `?moduleRoom=` answers 301 to it). A module's manifest says whether it supports docked and floating; the choice, the docked width and the floating box are remembered per module in `localStorage`. When the whole call is popped out, the modules follow it into the popup window (each module is opened again there, because a frame moved between windows would reload). A space's modules come from `/api/modules/for-space` and are turned on per space from the space's own settings; one whose `surfaces.canvas.menu` is `false` is left out of the menu and never opened or restored (the Assistant).
- **The Lobby** (plan-modules, "the Lobby is for being together", GitHub #63). The Lobby is social: chat, the conference, and modules whose manifest declares `surfaces.canvas.lobby: true` (the Calendar, from 1.17.15). `ModuleManager.onInSpace()` and `modules.isOnIn(id, spaceId)` in `server/modules.js` are the one check for whether a module is on in a space (`allSpaces` or `spaces`, and the Lobby only with the field); `moduleSpaceAccess()`, the reads across spaces, a space's module settings and the live change stream all use it. `allSpaces` keeps its stored meaning, "every space this module may be in". `modules.lobbySync()` runs after each environment build's bundled updates, and after a rollback, and takes `lobby` out of `spaces` for any module whose active version doesn't declare the field; its Lobby data is kept. The refusals and their sentence are in [api-modules](../api/api-modules.md). On the pages, Manage's "Available in every space" carries "(not in <Lobby>)" for such a module, and the Lobby's own settings page lists only modules made for it (`public/space-settings.js`).
- **A module's colour.** A manifest may name one of the theme's eight tints in `color` (`cleanColor()` in `server/modules.js`; [api-modules](../api/api-modules.md)). The host draws it, never the module: `data-tint` on the module's icon in its titlebar and its line in the Layout menu's Show section, and on its messages in Chat, where CSS turns it into `--tint` ([design-theme](../designsystem/design-theme.md), "Tints"). The AI is gold. The tint tokens also reach every module page, in `/sdk/host.css` and with the theme the host hands a frame, so a module can use them too. Bundled: Research blue, To-do green, Calendar red, the Planner teal, Polls purple, Places orange, Maps pink.
- **Notifications.** `public/brand.js` also opens the notification stream on each page (not in overlay pages, which read the counts once and leave the stream to the page underneath), shows a toast per notification, and keeps the unread counts on the top bar's bell, the home tiles and the space bar's Layout button. The bell's list shows the notices and marks them read (see [architecture-navigation](architecture-navigation.md), "The bell").

### Uninstall

Uninstalling removes the versions and the registry entry. With the data deleted too, it also forgets the module's schedules and notifications and drops its cached data.
